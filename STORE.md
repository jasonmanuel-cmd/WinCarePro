# Microsoft Store (MSIX) publishing

The MSI is the primary download. This MSIX exists for one reason: **the Store
signs the package for us**, which is the only way to get an authenticode
signature without paying $70-500 a year for a certificate. That removes the
SmartScreen "Windows protected your PC" warning that every MSI customer sees on
first launch.

This is a second distribution channel, not a replacement. Both ship identical
binaries from the same publish output.

## Build

```powershell
.\build-msix.ps1
```

Outputs `installer\WinCare.msix`.

The script needs no Windows SDK. `makeappx.exe`, `signtool.exe` and `makecat.exe`
all come from the `Microsoft.Windows.SDK.BuildTools` NuGet package, which the
script discovers in the local NuGet cache.

It runs the full test suite first and refuses to package on failure, then
verifies the built package contains the manifest, all 7 referenced assets, and
every published runtime file. A package that builds but is missing a file
installs and then fails to launch.

## What is committed

| Path | Committed | Why |

| `installer\AppXManifest.xml` | yes | Source. Placeholders are substituted at build time. |
| `installer\AppxAssets\*.png` | yes | Generated by `Tools\MakeIcon`, but versioned so artwork changes are reviewable. |
| `build-msix.ps1` | yes | The build itself. |
| `installer\WinCare.msix` | no | Build output. |
| `installer\AppXManifest.build.xml` | no | Generated during build. |
| `msix-stage\` | no | Staging directory. |

Regenerate the artwork after changing the mark:

```powershell
dotnet run --project Tools\MakeIcon -c Release -- Assets\WinCarePro.ico --assets installer\AppxAssets
```

## Known limitation: signing is not working yet

**The package builds and validates, but `signtool` cannot sign it on this
machine.** It fails with:

```
Error: SignerSign() failed. (-2147024885/0x8007000b)
SignTool Error: An unexpected internal error has occurred.
```

What was ruled out:

- Not the certificate. The same certificate signs an `.msi` and a renamed ZIP
  successfully (`Successfully signed`), so the key, chain and export are fine.
- Not the timestamp. Fails identically with and without `/tr`.
- Not `/p7` catalog signing, `/nc` uncompressed packaging, or the key's CSP.
  All three were tried with an explicitly configured RSA-1024/2048 legacy CSP.
- Not file size or count.

This is an unresolved interaction between this `makeappx`/`signtool` build and
MSIX package signing. It was not diagnosed further because the Store path does
not need it.

**Consequence:** the unsigned `.msix` cannot be sideloaded. Windows rejects it
with `0x800B0100, No signature was present in the subject`. That is a Windows
policy, not a package defect.

### To sign for local testing

```powershell
$env:WINCARE_SIGN_PFX = '<path to cert.pfx>'
$env:WINCARE_SIGN_PWD = '<password>'
.\build-msix.ps1
Add-AppxPackage -Path installer\WinCare.msix
```

The script prefers these variables over the self-signed fallback.

## Submitting to the Store

The unsigned package is exactly what Partner Center wants. Microsoft signs it.

1. Create a Partner Center account and reserve the identity name
   `WinCarePro.WinCareDesktop` (this is a DNS-style name and must be unique
   across the Store; if it is taken you must change `Identity/@Name` in the
   manifest).
2. Note the Publisher value Partner Center assigns you. It is a certificate
   subject like `CN=Contoso, O=Contoso Inc, L=Redmond, S=WA, C=US`.
3. Set both so the manifest matches:

   ```powershell
   $env:WINCARE_MSX_PUBLISHER = 'CN=..., O=..., L=..., S=..., C=...'
   $env:WINCARE_MSX_PUBLISHER_DISPLAY = 'Your Company Name'
   .\build-msix.ps1
   ```

   `Publisher` must match the certificate exactly or the package will not
   install. `PublisherDisplayName` is what users see in the Store listing.

4. Upload `installer\WinCare.msix`.

### Things the Store submission will ask about

Be ready to answer these; they come up in the questionnaire and an unclear
answer stalls certification.

**`runFullTrust` (restricted capability).** This app is a WPF desktop
application calling Win32 APIs directly: `powrprof` for power plans, `psapi`
for per-process working sets, and `EmptyStandbyList` for the standby cache.
There is no sandboxed equivalent. This is normal for a PC maintenance tool but
it is a restricted capability and is reviewed.

**`internetClient`.** Declared solely for the opt-in "Check for updates"
action, which performs one user-initiated HTTPS GET. There is no telemetry, no
analytics, no crash reporting service and no background network activity. This
is documented in `PRIVACY.md`.

**Administrator behaviour.** The app does not request elevation by default. DNS
changes and some uninstalls need it, and the user is prompted only when they
attempt one of those specific actions.

## Known differences between the MSI and Store builds

Nothing is stubbed out, but packaging changes the environment:

- **Data location — UNVERIFIED, check this before submission.** The app writes
  `history.json`, `crash.log` and `environment.txt` under
  `Environment.GetFolderPath(SpecialFolder.LocalApplicationData)`. For a
  packaged app that API is documented to redirect into
  `AppData\Local\Packages\<PFN>\LocalCache`, which would mean the paths in
  `PRIVACY.md` are wrong for a Store install.

  This was **not confirmed on a real install**, because the package cannot be
  signed here (see above) and so cannot be installed. Treat it as a known
  unknown: install the signed package, check where the three files appear, and
  correct `PRIVACY.md` if they moved. Supporting documentation that names the
  wrong path is a real support problem, so do not skip this.
- **Update check.** `update-source.txt` must be in the package root. It is
  included via the publish harvest.
- **Uninstall.** The Store handles removal, not the MSI. Whether
  `history.json` survives a Store uninstall is also unverified; the MSI
  behaviour is covered by tests, the Store behaviour is not.
