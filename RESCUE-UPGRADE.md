# WinCare Rescue upgrade — requested scope

User requests older-PC rescue: useful memory relief, reducing unnecessary background activity, malware scanning/remediation, strong harmful-removal protection, and an Options menu. This authorizes product development, not executing dangerous changes on the current PC. No guarantee of like-new performance or zero risk.

## Sequencing
The existing usefulness worker owns source edits until finished. This phase is queued; do not introduce competing source writers. Next create implementation acceptance tests against actual current architecture, then implement and independently verify.

## Requirements
1. Memory and background apps: show measured RAM and sampled CPU, distinguish RAM from disk storage. Show user-owned eligible apps and reasons for recommendations, not classify every background process as unnecessary. Allow only explicit individually confirmed graceful close requests for verified ordinary user apps, warn about unsaved work, never force-kill or terminate trees by default. Revalidate PID/start time/path/session before action; unknown identity or protected role fails closed. Preserve Windows, security, drivers, accessibility, sync, remote access and agent runtimes. Do not add blanket working-set/standby flushing, service disabling, or misleading freed-RAM/speedup claims. Provide reversible reviewed startup changes through existing service. No automatic closing.
2. Malware: integrate supported Microsoft Defender capabilities, not a homegrown scanner. Read status/availability/signature freshness; unavailable/passive/error must not appear clean. User-initiated quick/full scan with explicit disclosure that Defender may remediate according to its policy. Verify scan identity/completion/cancel/error instead of treating process start or empty history as clean. Expose detected threats and Windows Security quarantine/protection-history workflow; no independent arbitrary file deletion, security disabling, exclusions changes or automatic offline reboot. User-approved elevation only. Unit tests use fake runners, never start a host scan or remediate host files during development.
3. Safety: central fail-closed action eligibility plus exact-target confirmation and audit; protected root/system/security data stays blocked, including reparse/path escape. Unknown targets remain protected. No registry cleaner, driver/firmware/voltage changes, uninstall-all, kill-all, or permanent fallback. Preserve backup/readback/conflict-aware recovery for supported reversible operations. Explicitly disclose that graceful close/uninstall/remediation are not automatically reversible.
4. Options: low-resource UI refresh interval, reduced animation, theme/accessibility if supported, confirmation preferences that cannot disable critical safeguards, local diagnostic privacy controls, reset APP preferences only. Persist atomically to isolated injectable settings store; schema migration/corrupt-save failures visible. No run-at-login or background service enabled by default; scheduler and security consent remain separate.
5. Low overhead: bound polling, cancel on navigation/close, no duplicate scans, no always-on heavy scans. Show measured benefit before/after only for comparable samples, never promise hardware restoration.
